# GitHub Pages + Supabase online storage

The Supabase edition is prepared on the `supabase-storage` branch. Do not deploy the new `index.html` until `setup.sql` has been run successfully in the destination project. Existing GitHub Pages stays unchanged until activation.

## One-time database setup

1. Open the Supabase project's SQL Editor and create a new query with `+`.
2. Paste the **entire contents** of `setup.sql` and click **Run**. It can be rerun and retains existing rows, including tables created earlier in this conversation.
3. Confirm `Success. No rows returned`.
4. The public configuration is in `public/cloud-storage.js`: project URL + `sb_publishable_...` key only. No database password, secret key, or service_role key belongs in this repository.
5. After setup succeeds, publish the prepared code to `main`. GitHub Pages remains `main / (root)`.

## Development and build

```sh
npm ci
node build-preview.js
npm start
```

Both the server-served UI and the generated root `index.html` call Supabase. `build-preview.js` no longer swaps the API for localStorage. There is no offline fallback that pretends to save online. The existing Node SQLite API remains for compatibility and its regression test; it is not used by the Supabase browser client.

Share URLs use `/oiocha-tea-project/#garden/<random-UUID>` so GitHub Pages can serve every cup without a server rewrite. The ID survives reload. Share links omit the cache-busting query string. The original demo's localStorage is left untouched; old browser-only cups are not automatically uploaded or shared by the new code. No current Supabase rows are deleted during setup or builds.

## Access model

This is a login-free rolling-paper demo: anyone with a random cup link can read that cup, write a message and move its leaves. Treat the link as the access key. It does not authenticate the person holding it. Do not place confidential or sensitive personal information in messages. There is no whole-site list/search endpoint, cross-cup message update, public table access, delete endpoint, or permission to edit message text. New UUIDs are generated by Postgres, not sequential IDs.

RLS is enabled. `anon` and `authenticated` have no table privileges. Four narrowly scoped SECURITY DEFINER functions with an empty search_path perform validated operations and filter by exact cup ID; the movement RPC also requires that the message belongs to the specified cup. Each function's default PUBLIC execution grant is revoked explicitly.

Basic spam controls are enforced inside transactions: max 20 messages/minute/cup, 500 total messages/cup, 60 new cups/minute/site and 10,000 stored cups/site. Advisory locks serialize the quota checks with insertion. These are demo limits, not unique-user counting or robust bot protection. A distributed bot can consume shared quotas; a public campaign should add a server-side CAPTCHA/rate limiting and authenticated ownership before promotion or rewards. Message count does not represent distinct participants. Database administrators can adjust limits in the SQL after review.

## Validation

`npm test` runs the original SQLite API regression and real PostgreSQL-engine tests through PGlite, including role grants, invalid input, quotas and cross-board isolation. Test dependency is development-only.

`node tests/cloud-browser.cjs` additionally requires Playwright and Chromium (override `CHROMIUM_PATH` if needed). It serves the generated HTML and routes its real RPC requests to a PGlite PostgreSQL engine with the `anon` role. It verifies independent desktop/mobile browser contexts, share URL, cross-device updates, reload, position saves, HTML escaping and isolation. This is a local integration test, not proof of a live Supabase deployment.

After SQL installation and GitHub deployment, manually create a cup, post a message, copy its link into a separate device/incognito session, write a second message, verify it appears within 3 seconds on the first device, reload both, and open a different cup to verify isolation. Live readiness is pending until these checks pass.

If RPC reports `PGRST202`, setup.sql has not been run or the schema cache is stale; the script issues `NOTIFY pgrst, 'reload schema'`. Do not remove RLS or grant direct table access to work around an incomplete setup. If keys or network access fail, resolve the project settings rather than using a service_role key in a browser.
